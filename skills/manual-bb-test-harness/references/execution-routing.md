# 実施の仕分け（LLM と手動）

手動ブラックボックスのケースを、LLM のエージェントが画面や端末を操作して実施できる項目と、人が実施する項目に分ける。分けるのは実施する主体だけで、観点・oracle・優先度の決まりは変えない。

## 自動テストとは別に扱う

| | 自動テスト | LLM が実施 | 手動 |
|---|---|---|---|
| 何か | リポジトリにあるテストコード。同じ確認を毎回くり返す | 手動ケースの手順を、LLM が操作して実施する | 手動ケースの手順を、人が実施する |
| 証跡 | `automation_evidence`（suite の成否と件数） | `execution_evidence`（ケースごとの期待と実際、添付） | `execution_evidence` |
| リスクの補正 A | 付く | 付かない | 付かない |
| Gate | 自動証跡の条件 | 手動の実行結果の条件 | 手動の実行結果の条件 |

LLM の実施は、次の変更でも同じ確認がくり返されることを保証しない。自動テストの代わりに数えず、補正 A の根拠にもしない。くり返し実施して安定したケースは、自動テストへ移す候補にする。

## 仕分ける単位と書き方

- 期待結果の 1 項目ごとに仕分ける。1 つのケースに LLM と手動が混ざってよい。
- ケースの表の `executor` に、`LLM` か `手動：理由` を書く。手動には、手動に残す条件のどれに当たるかを書く。
- 混ざるケースは、手順に「（人が行う）」「（LLM が行う）」を書く。
- `LLM` は「LLM が実施できる」の意味で、人が実施してもよい。
- blocked の項目と `[要確認]` の項目も仕分けは付ける。手順の書き換えは、実施できるようになってから行う。
- 前提にした LLM の道具（ブラウザの操作、端末やシミュレーターの操作、API やログの読み取り）と、入れる環境を、テスト計画に書く。前提を書けないときは手動にする。

## 手動に残す条件

次のどれかに当たる項目は手動にする。言葉ではなく、その手順が実際に何を要るかで決める。カメラを使う手順でも、写るものが何でもよいなら LLM で回せる。

| 条件 | 例 |
|---|---|
| 画面や端末の外の物が要る | 実プリンタと用紙、読み取り機、定規での計測 |
| LLM の道具が届かない画面を操作する | OS の印刷ダイアログ、別のアプリの画面 |
| 人の感覚でしか判定できない | 読み上げを聞く、色味、使い心地 |
| LLM にさせない操作を含み、準備として切り出せない | 実在の認証情報の入力、本番のデータの変更、実際の支払い、実在の相手への送信、本人確認 |

## LLM で回せる形に書き換える

手動に当たる項目も、次の書き換えで LLM に回せるなら書き換える。期待結果の文言・値・根拠と、判定の数は変えない。

- 準備と実施を分ける。ログイン、認証、データやファイルの用意は人が済ませ、前提条件に書く。LLM は用意された状態から操作する。
- 見た目の確認を、値の読み取りに置き換える。位置・幅・時刻・文字を、画面から読める値で判定する。
- 届かない部分を差し替えて、その先を確かめる。差し替えてよいのは、確かめたい動きが差し替えた部分の結果だけに頼っていると、根拠で示せるとき。差し替えた部分そのものは、別の手動の項目で確かめる。
- 紙や実機の代わりに、同じ内容を写したもの（印刷用の PDF など）で確かめる。実機でしか出ない違いは手動に残す。

書き換えで確かめる内容が狭くなったときは、狭くなった分を手動の項目として残す。

## 実施と証跡

- 実行証跡の `tester` に、LLM であることとモデルの名前を書く。
- 期待結果の 1 項目ごとに、観測した値と証跡（画面の写し、読み取った値、応答やログ）を残す。「表示された」だけで pass にしない。
- 手順どおりに進められないときは blocked にして理由を書く。手順にない操作で通したときは pass にしない。
- LLM が pass にした P0 の項目は、人が証跡を確かめたことを記録してから Gate に数える。
- LLM と手動の件数、手動に残した理由を、テスト計画に書く。

JSON の `manual_case_set` には実施の仕分けを入れる項目が無い。Markdown のケースの表と、実行証跡の `tester` に書く。
